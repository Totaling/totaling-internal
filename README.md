# @totaling/internal

Внутренние вызовы между сервисами Totaling: **клиент**, который берёт у auth
токен сервиса и ходит с ним к другим API, и **middleware**, которым сервис-
владелец закрывает свои внутренние маршруты.

Зачем: по ADR-0002 сервисы получают чужие данные через HTTP-API владельца, а не
SQL по чужой схеме; по ADR-0009 lab, manager и кабинет ученика развязываются
именно так. План — `../docs/LAB_DECOUPLING_PLAN.md`, этап 0.

## Как это устроено

```
сервис A ──(clientId + секрет)──▶ auth  POST /auth/internal/v1/token
         ◀── JWT RS256: aud=internal, sub=A, scope=[права A], 15 минут

сервис A ──(Bearer, напрямую на 127.0.0.1)──▶ сервис B  /internal/v1/…
                                               requireInternal('право')
```

- Токен сервиса подписан тем же ключом auth, что и пользовательские. API уже
  проверяют пользовательские токены этим ключом — новых ключей не нужно.
- **Пользовательский токен на внутреннем маршруте не пройдёт** (`aud` другой), а
  токен сервиса не пройдёт на пользовательском.
- Права сервисов перечислены **в auth** (`src/internalClients.js`), проверяет их
  **владелец** маршрута.

## Установка (git-зависимость по тегу)

Как `@totaling/storage`:

```jsonc
"dependencies": {
  "@totaling/internal": "github:Totaling/totaling-internal#v0.1.0"
}
```

`jsonwebtoken` — peer-зависимость: используется копия, которая уже стоит в API
(у них разные мажорные версии, двух копий в одном процессе не будет).
Нужен node 18+ (встроенный `fetch`).

## Клиент

```js
const { createInternalClient } = require('@totaling/internal');

// из окружения — так в API (переменные ниже)
const internalApi = createInternalClient.fromEnv();

const content = await internalApi.get('lab', '/internal/v1/content', { uids: ['…', '…'] });
await internalApi.post('manager', '/internal/v1/content-deleted', { uid });
```

| Переменная | Пример | |
|---|---|---|
| `INTERNAL_AUTH_URL` | `http://127.0.0.1:3004` | auth, напрямую |
| `INTERNAL_CLIENT_ID` | `client-api` | имя из реестра auth |
| `INTERNAL_CLIENT_SECRET` | … | секрет этого сервиса, **только в `.env`** |
| `INTERNAL_URL_<СЕРВИС>` | `INTERNAL_URL_LAB=http://127.0.0.1:3002` | по одной на каждый сервис, к которому ходим; имя после `INTERNAL_URL_` — то, что передаётся первым аргументом в `get`/`post` |

Адреса не угадываются: порты у окружений разные (прод 3001/3002, staging
3031/3032). Без обязательной переменной сервис падает **на старте** со списком
недостающего, а не на первом вызове. Несекретное удобно держать в
`ecosystem.config.js`, секрет — в `.env`.

Поведение:

- токен держится в памяти и обновляется **заранее** (по умолчанию за 60 с до
  истечения); одновременные вызовы делят **один** запрос к auth;
- `401` от владельца (например, auth перевыпустил ключ) — токен сбрасывается,
  вызов повторяется **один** раз;
- остальные ошибки не повторяются: бросается `InternalCallError` с полями
  `service`, `method`, `path`, `status` (`0` — ответа не было: таймаут или
  сеть) и `body`;
- таймаут по умолчанию 5 с (`timeoutMs`);
- секрет не попадает ни в текст ошибок, ни в логи.

## Middleware владельца

```js
const { requireInternal } = require('@totaling/internal');
const { publicKey, issuer } = require('../authKey');          // уже есть в каждом API

const internal = requireInternal({ publicKey, issuer });

router.get('/internal/v1/content', internal('lab:content:read'), controller.contentByUids);
```

По порядку: запрос через nginx (`X-Real-IP` / `X-Forwarded-For`) → `404`;
нет или негодный токен (подпись, issuer, `aud=internal`, срок) → `401`;
нет права → `403` и строка в логе, кто и куда стучался; иначе
`req.service = { id, scope }`.

### Правила

- **Внутренние маршруты — под `/internal/v1/…`, вне `/api/`.** На api-хостах
  nginx отдаёт наружу только `/api/…`, так что снаружи их нет по построению.
  `requireDirect` внутри — второй рубеж.
- **Право указывается у каждого маршрута.** `internal()` без аргумента падает
  при подключении: маршрут без права — ошибка конфигурации, а не «всё можно».
- Маршрут узкий, под конкретную задачу. Владелец доверяет вызывающему сервису
  (например, что client-api спрашивает про ученика из проверенного токена), и
  чем уже маршрут, тем меньше это доверие стоит.

## Секреты

Пара «секрет + хеш» — в auth:

```bash
cd totaling-auth && npm run gen-internal-secret client-api
```

Секрет — в `.env` вызывающего сервиса, sha256 — в `.env` auth
(`INTERNAL_SECRET_SHA256_CLIENT_API`). Свой секрет на каждое окружение. Новый
сервис или новое право — правка `totaling-auth/src/internalClients.js`.

npm test     # node:test; настоящие HTTP-серверы: поддельный auth и сервис-владелец
